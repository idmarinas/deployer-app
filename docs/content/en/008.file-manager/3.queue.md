The **Transfers** tab shows one block per job, newest to oldest. Each block gathers direction, status, file count, transferred bytes —available when the item finishes—, source and target paths and the error message when present, regardless of status. The queue is stored in the local database: it persists after switching sections, reloading the window or closing and reopening the app.

## Inspect a block's detail

Below the header appears the job's file tree, always expanded and read-only. Before copying anything, the backend enumerates the source recursively; the detail receives sizes as soon as each item starts (`file_list` event), not while the job is pending. The detail uses the same order as the panels: folders first, files after, and within each group natural alphabetical order according to the language, ignoring accents and case. Directories are synthesized from paths and the entry type from the pre-list is not preserved, so the order of symbolic links may not match the panels. Transferred bytes, percentage and status appear **to the left of the name**, with the progress bar and any error below the row.

::note
Per-file progress is updated while copying, with a minimum of 100 ms between progress events, except for the final event and files that finish in the first block. The header receives the aggregate bytes when each item completes successfully; on error or cancellation that event is not emitted and files already copied are not counted.
::

## Retry a transfer

**Retry** appears on every block, including pending or running ones. Pressing it creates a new job with the same paths and options —linked to the previous one via `retry_of`—; the previous job stays in the history as a reference. The button is disabled when the host is not in the list of enabled hosts loaded on opening, and the notice says **The server is no longer available**; a host change while the app is open does not refresh that list until reload.

Jobs that were **pending** or **running** when the app closed come back as **Interrupted**: their cancellation tokens no longer exist in the new session. Retrying them creates a job that copies again from the source, it does not resume already written bytes; they are not started automatically on open.

## Stop a transfer

**Cancel item** appears only while the job is pending or running and also works from tree nodes. The backend registers all tokens when the batch starts, so an item that has not started can also be cancelled: it becomes **Skipped** instead of **Cancelled**. The partial file being written is discarded —deletion is best-effort—; files already completed are kept and the other jobs in the batch continue.

## Adjust concurrency

The **Simultaneous transfers** field above the queue sets how many jobs can be running at once, with the text **Up to {count} at a time**. It accepts **1 to 16**, defaults to **2** and is saved as a preference. The value is sent in the next batch you start, not in those already running.

::note
The batch keeps one SSH/SFTP connection per server. All concurrent jobs share that session; the limit only controls how many are running at once.
::

## Clear the queue

**Clear finished** removes all blocks in a terminal status —completed, error, cancelled, skipped or interrupted— and their rows in the database. Pending or running jobs are untouched. There is no retention limit: blocks accumulate until you press that button. The database deletion is asynchronous, so closing the app right after pressing it may delay it.

::note
No remote management operations are offered to the user: you cannot create folders, rename, delete or edit content. During copying, directories are created, `chmod` is applied on upload and the partial file is deleted if cancelled.
::
