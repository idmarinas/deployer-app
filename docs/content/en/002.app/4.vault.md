**:vars{n="project"}** stores sensitive data **encrypted** in the local database. This page describes the technical mechanism; the reporting policy is in [Security](/security).

## What is encrypted

Fields declared as `encryptedText(...)` in the Drizzle schema are encrypted:

| Field | Table | Condition |
| --- | --- | --- |
| `password` | `deployer_hosts` | Always |
| `key_content` | `deployer_passkeys` | Always |
| `passphrase` | `deployer_passkeys` | Always |
| `value` | `deployer_variables` | Only when the variable is secret |

## How it is encrypted

- The algorithm is **AES-256-GCM** with a **random 12-byte nonce** per operation.
- Encrypted values are stored in the database with the format: **`ENC:{version}:<base64>`** (`nonce` + `ciphertext`).
- The vault (`vault.hold`) and the 32-byte *salt* are stored in the application's local data directory.

## Versioned keys

Each field has its own key, versioned by scope:

```text
encrypt:{table}.{column}:{version}
```

This allows **rotating** a key without losing data: when rotating, previous versions are preserved and old values can be **re-encrypted** with the current version. Key rotation and re-encryption are managed from the app's Security settings.

## Who writes and who reads

- The **frontend is the only writer** of the vault: it encrypts on save, decrypts or **masks** on read.
- The **Rust backend opens the vault in read-only mode** (`StrongholdVault::open`) to decrypt credentials when establishing an SSH/SFTP connection.
- On read, the Drizzle proxy replaces encrypted values with `BLANK_VALUE` so the interface **never** receives raw encrypted content, unless explicit decryption is requested.

## Vault password and keychain

- The vault password is **randomly generated** (64 hexadecimal characters) on the first run.
- It is stored in the **operating system keychain** using the `keyring` crate.
- The vault key is derived with **Argon2** from that password and the *salt*.

## Vault health check

:labels-version{version="0.1.1" is-new size="sm"} On startup, the application checks the vault state in a non-blocking way: whether the file exists, whether the snapshot loads, whether the `encrypt-keys` client is present and whether keys are missing.

::note
Even if someone accesses the database file, they cannot read credentials or secrets without the vault key, which resides in the system keychain.
::
