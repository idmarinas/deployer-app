When you start :vars{n="project"} for the first time, the application runs an **automatic diagnostic** and redirects you to the screen needed to get the database ready.

## Startup diagnostic

On startup, the frontend checks in a non-blocking way:

1. The **Stronghold vault** state (file, snapshot and `encrypt-keys` client).
2. Whether the **database exists** (`check_database_exists`).
3. Whether there are **pending migrations** (`has_migrations_pending`).

Depending on the result:

| Situation | Redirect |
| --- | --- |
| The database does not exist | `/deployer` — initial setup wizard |
| It exists, but there are pending migrations | `/deployer/migrations` — run migrations |
| It exists and is up to date | `/dashboard` — normal app use |

## Setup wizard

The setup screen (`/deployer`) shows a step guide with the process order. From there you can:

- **Select SQLite file** — choose an existing `.sqlite` file. The application validates it, runs pending migrations if needed, saves the path and completes the initial seed.
- **Create new SQLite file** — create a new file (suggested name `deployer-app.sqlite`), initialize the database, run migrations, validate the result, save the path and complete the initial seed.
- **Restart setup** — retry the process if any step fails.

## Initial seed

When the initial setup is completed, the application runs a data seed:

- **Initial settings** — when creating a new database, `locale` and `theme_color` are saved in the `settings` table.
- :labels-version{version="0.2" is-new size="sm"} **Internal commands** — internal commands are inserted or updated without duplicating them, both when creating a database, loading an existing one or running pending migrations.

## Pending migrations

If the database exists but has pending migrations, the app takes you to `/deployer/migrations`. From that screen you can run migrations, validate the database and complete the initial seed; if a step fails, you can restart the process.

Once completed, the app continues to `/dashboard`.
